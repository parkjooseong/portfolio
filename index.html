개발 배경

계약 내용을 충분히 이해하지 못한 채 불리한 조건을 받아들이는 소상공인의 문제에 주목했습니다. 부산 관광상권 소상공인이 광고대행 계약을 확인하고 조정을 준비할 수 있도록, 팀이 AI 계약 관리 서비스를 만들었습니다.

담당 업무

백엔드를 맡아 데이터베이스를 관리하고 연결했습니다. 여러 외부 API를 연동하고 동작을 검증하며, 팀이 만드는 기능에 필요한 데이터가 이어지도록 작업했습니다.

개발 노트 중복 요청과 계약 상태의 일관성

같은 요청이 두 번 와도 작업은 한 번만

응답이 늦어 사용자가 분석이나 조정 요청을 다시 보내면, 같은 작업이 중복 실행될 수 있습니다. 외부 API를 연결하는 과정에서 새 요청과 이전 요청의 재시도를 구분할 필요가 있었습니다.

요청 식별자인 Idempotency-Key와 요청 내용의 해시를 함께 비교하도록 구성했습니다. 같은 키·같은 내용은 기존 처리 결과를 돌려주고, 같은 키로 다른 내용을 보내면 409 오류로 거절합니다. 같은 요청이 동시에 들어와도 먼저 시작한 작업의 결과를 기다립니다.

회귀 테스트는 반복·동시 요청에서 실제 처리 함수가 한 번만 실행되는지, 같은 키의 요청 내용을 바꾸면 충돌로 처리되는지를 확인합니다.

계약 상태와 변경 이력을 함께 저장하기

계약 상태만 바뀌고 타임라인 기록이 빠지면, 사용자는 현재 단계와 처리 과정을 다르게 보게 됩니다. 여러 기능을 연결하면서 두 데이터를 따로 저장하지 않도록 저장 경계를 맞추는 것이 중요했습니다.

Supabase의 PostgreSQL 함수에서 현재 상태 확인·상태 변경·이력 저장을 하나의 트랜잭션으로 처리합니다. 예상한 현재 상태와 DB 상태가 다르면 갱신하지 않아, 뒤늦게 도착한 요청이 다음 단계를 덮어쓰지 않도록 했습니다.

저장소 단위 테스트에서는 상태와 이력이 하나의 DB 함수 호출로 전달되는지, 상태 불일치 결과를 호출한 쪽에 돌려주는지를 확인합니다.

개발 배경

사람들에게 잘 알려지지 않은 책 중에도 지금의 관심사와 연결되는 책이 많습니다. 대출이 적다는 이유로 놓치고 있던 책을 다시 발견할 수 있도록, 팀은 도서관 데이터와 트렌드를 연결하는 추천 서비스를 만들었습니다.

담당 업무

추천·회원·사서 기능을 위한 백엔드 API와 인증, DB 설계를 담당하고 외부 데이터를 연동했습니다.

개발 노트 추천 후보 확보와 외부 데이터 정합성

CSV가 없는 도서관에서도 추천을 시작하기

초기에는 사서가 대출목록 CSV를 올려야 추천 후보를 만들 수 있었습니다. 업로드가 없는 도서관에서는 추천할 책 자체가 없어, 이용자가 서비스를 시작하지 못하는 제약이 있었습니다.

정보나루의 장서 목록과 대출 순위를 대조해 조회한 대출 순위 밖의 책을 후보로 수집하는 경로를 추가했습니다. 청구기호와 소개글 등 필요한 정보를 갖춘 도서만 남기고, 여러 외부 조회가 필요한 수집은 비동기 작업으로 분리해 작업 ID로 진행 상태를 조회하도록 구성했습니다.

순위 밖이라는 사실이 실제 미대출을 뜻하지는 않습니다. 실제 대출 횟수가 있는 CSV 후보를 우선하고, 일반 이용자가 이를 API 후보로 덮어쓰지 못하도록 권한을 검사합니다. 회귀 테스트에는 순위 내 도서 제외와 CSV 후보 보호 조건을 포함했습니다.

후보 수집 코드 (새 탭)CSV 후보 보호 테스트 (새 탭)

ISBN 차이로 후보 저장이 실패하는 문제

장서 목록에서는 다른 ISBN으로 들어온 두 항목이 외부 상세 조회 후 같은 ISBN으로 반환되는 문제가 있었습니다. 수집 전에만 중복을 제거하면 DB의 도서관·ISBN 유일성 제약에 걸려 후보 저장 전체가 실패할 수 있었습니다.

중복 검사 기준을 수집 시점의 번호에만 두지 않고, 실제로 저장할 상세 정보의 ISBN으로 저장 직전에 다시 중복을 제거했습니다. 후보 교체는 별도 Spring 서비스의 트랜잭션에서 처리하고, 새로 확보한 후보가 0권이면 기존 목록을 유지합니다.

회귀 테스트는 서로 다른 두 입력이 같은 ISBN으로 반환될 때 한 권만 저장되는지, 소개글 품질 기준을 통과한 책이 없을 때 기존 후보 교체를 호출하지 않는지를 확인합니다.
